# Changes — 2026-11-17 (`agentic_dataset`)

This document records the changes made on 2026-11-17 to the per-article agentic Legal-AMR pipeline, its demo, and its plan drawing. No external model API was called; the SPRING graphs and the demo answers were produced locally and checked by the real agent/validator.

## Summary

- Fixed real defects in corpus search, mention resolution, metadata cleaning, rewrite validation, and coverage reporting.
- Fixed a resolver bug exposed by per-sentence memory: a generic memory match (head-only, e.g. “the Court” vs a remembered court) no longer outranks a name stated in the current sentence.
- Generated real SPRING base graphs for the six demo sentences and stored them.
- Built a reproducible, sentence-by-sentence demo on article 5772 (real corpus, resolver, cached wiki, agent, validator): **5 accepted, 1 rejected, 4 rewrites, 0 repairs** in the main run, plus a separate **real repair demo** (broken first answer → validator error → fixed, accepted).
- Replaced the six-sentence drawing walkthrough with **one** sentence (360450) shown as it transforms over time: nine moments from arrival to saved record, each with the sentence as it stands at that moment, the real tool results, both graphs, the validator output and the memory before/after, plus a changed/stayed summary.
- Extended that treatment to **all six** sentences of article 5772 as a side-by-side grid (rows = the nine moments, columns = the sentences), including the rejected one, with a card that explains the rejection; streamlined the pipeline drawing from ten steps to seven, with the SPRING base graph handed over first.
- Made the SPRING graph first in the real pipeline too: `base_amr` is the first field of every sentence in the batch and repair payloads, the system prompt has a `BASE GRAPH FIRST` rule, and a real run refuses to start without base graphs.
- Updated `README.md` and `checklist.md` to document the demo, SPRING source, score formulas, and the repair example.

## Code changes

### `corpus.py`
- **`article_search` / `Corpus.search`**: when `before_sentence_id` is given, returns only earlier sentences (`sentence_id < before`), nearest first, and never the sentence being resolved. Distance is computed from the target sentence.
- **`resolve_mention` offer/cleaning**: keeps a closing parenthesis that closes an earlier one (e.g. `section 2(2)` is no longer stripped to `section 2(2`); junk metadata fragments containing `". "` or ending with a period are dropped from `Article.metadata()`.
- **Same-sentence resolution**: a mention can resolve to a name that appears **before** the mention in the same sentence (e.g. 360465 “before the Supreme Court, the Court noted…” → Supreme Court, score **0.970**, evidence 360465).
- **Generic ledger match (bug fix)**: an exact name/alias already in the ledger still scores **1.000**. A generic mention that only shares the head with a remembered name is treated as a hint, not proof, and scores **0.860** so it cannot outrank a name stated in the sentence. (Before this fix, 360465 incorrectly preferred a remembered “Delhi High Court” at 1.000 over “Supreme Court” stated in the same sentence.)

### `rewrite.py`
- Name comparison strips a leading article and ignores case (`_name_key`), so a replacement like `"the Supreme Court"` validates correctly against the graph/name in the sentence. Edit-backed and graph-name checks use this normalized comparison.

### `check.py`
- `coverage` is computed via `common.coverage` (content-word / light-stem coverage) instead of relying on the core-validator info, so reports carry the real coverage value.

## Score formulas (as documented and shown in the demo)

- **`resolve_mention`**: same sentence, name before mention → 0.970; earlier sentence with alias → 1.000 − min(distance,40)*0.001; earlier sentence without alias → 0.900 − min(distance,40)*0.001; article metadata → 0.800; exact name/alias in memory → 1.000; generic head-only memory match → 0.860. Credible if ≥ 0.700; ambiguous if top two differ by < 0.030.
- **`wiki_lookup`**: equal after normalization → 1.000; else 0.6*word overlap + 0.35 same year − 0.4 different year + 0.1 punctuation-insensitive match + 0.03 if description mentions “India”, capped at 0.99.
- **`coverage`**: content words = tokens with 3+ letters/digits minus stopwords; kept if token or light stem appears in graph; coverage = kept / total (rough). Kept and missing words are listed per sentence.

## Paragraphs in, SPRING as a tool (same day, after the drawing round)

The agent no longer receives pre-split sentences with a pre-computed base graph. It receives **whole paragraphs**, splits them itself, and asks the local SPRING parser for a graph through an ordinary tool call — one call per sentence, several calls per turn, executed in parallel. It never sees a corpus sentence id.

- **`spring.py` (new):** lazy wrapper around the local amrlib SPRING model (`~/.cache/amrlib/model_parse_spring-v0_1_0`, CPU). `parse(sentence)` returns the graph plus its own validity, node/edge counts and seconds; `parse_many()` exists for prewarming; a lock guards the model because amrlib is not thread-safe; an optional cache holds graphs from an earlier run; a missing model/package returns `status: unavailable` instead of raising. `--mock` may fall back to a placeholder graph when amrlib is absent; a real run preflights the model and exits if it cannot load.
- **`tools.py`:** new `spring_parse` tool: `{"sentence": "..."}` in, `{amr, status, errors, parser, model, n_nodes, n_edges}` out — a plain parser call, no ids, no article facts, no memory. Matching the text back to a corpus sentence (so the record can be keyed by `sentence_id`) happens inside the toolbox and never reaches the model. `article_search` and `resolve_mention` now take sentence **text** (`before`, `sentence`) instead of ids, with an error hint when the text is not a corpus sentence.
- **`llm.py`:** `run_tool_calls()` runs an assistant turn's tool calls concurrently (thread pool, at most 8) and returns results in call order, so the trace and tool messages stay aligned; a tool exception becomes an `{"error": ...}` result instead of killing the turn. Both the real client and the mock client use it, which is what makes four `spring_parse` calls from one paragraph actually run together.
- **`prompt.py`:** the batch payload is now `{"paragraphs": [{"para_index", "text"}]}` plus article, ledger; the system prompt rule is `PARAGRAPH IN, SPLIT, PARSE, EDIT` (split it yourself; call `spring_parse` once per sentence in one turn; never annotate a sentence you did not parse; you never see ids). Results are named by `original`, the exact text that went to `spring_parse`.
- **`agent.py`:** batches are whole paragraphs (`_paragraph_batches`, about `agent.batch_size` sentences each, checkpoint `next_index` in paragraph units); `_parse_results` attaches answers to corpus sentences by punctuation-insensitive text match (no positional fallback, so a paraphrased or merged sentence lands nowhere and is reported); a sentence with no graph from the tool fails as `no_base_graph` and is repairable; repair notes carry `original` + `base_amr` and no ids; new events `spring_graphs` (parsed/calls) and `answers_matched`.
- **`corpus.py`:** `Paragraph` (unsplit text = its corpus sentences joined) and `Article.paragraphs()`.
- **`run.py`:** base graphs are an optional warm cache, not a requirement; the real-run preflight loads SPRING; the mock script calls `spring_parse` for the whole batch in its first turn and then answers, and the mock path batches by paragraphs too.
- **`examples.py`:** the walkthrough renders `spring_parse` lines (`sentence -> SPRING 16n/23e (ok)`).
